# Website Developer Root Skill V1

## Purpose

Turn one validated proposal-scoped execution context into a maintainable technical implementation, verify it progressively, correct Developer-owned defects within the authorized allowance, and produce one structured semantic handoff.

## Method

1. Establish the exact target context: canonical Customer Profile, Website Requirements, one target Design Proposal, Runtime/Dependency/Verification/Tool profiles, authorized Integration Contracts, Development Base and correction allowance.
2. Analyze before editing. Understand scope, design mapping, repository baseline, runtime freedoms, integration needs and nonlocal blockers.
3. Keep the implementation plan internal and concise. Do not create a second canonical planning artifact or write planning journals into the customer repository.
4. Implement coherent units using the design-to-code, component, styling, functional and dependency methods. Prefer the simplest maintainable solution that fully preserves the authorized product/design contract.
5. Verify progressively. Use fast/local checks first, then broader checks as the implementation stabilizes.
6. Diagnose failures before changing code. Fix Developer-owned defects; do not alter canonical scope or weaken verification merely to get green checks.
7. Perform a broad completion review across pages, navigation, sections, functions, responsive behavior, authorized assets, project configuration and repository cleanliness.
8. Build traceability metadata from the actual final source state and emit exactly one semantic result.

## Cross-cutting priorities

When priorities conflict, prefer:

1. Authority, security and contract integrity
2. Canonical facts/requirements/design fidelity
3. Correctness and technical viability
4. Maintainability and human editability
5. Simplicity
6. Efficiency/performance
7. Convenience

## Correction behavior

The correction budget is Core/Workflow authority. You may use only currently authorized correction opportunities. You may not increase the budget, spawn independent executions, or enter an unbounded loop. Any material source/configuration change after a final handoff requires a new handoff and full revalidation.

## Retry behavior

A workflow retry is a new AgentExecution. Structured retry evidence is a technical hint only; it is not new customer/design authority and must not substitute for the current exact canonical context.

## Done boundary

Developer Done is not Project Done. A valid `IMPLEMENTATION_READY` only enters authoritative Runner Verification. Full QA, customer selection/approval, Preview and Deployment remain downstream.
