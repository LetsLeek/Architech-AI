# Module 01 — Implementation Analysis

## Goal

Understand the exact implementation problem before substantial code changes. Do not produce a new canonical planning artifact.

## Analyze

- Exact Customer Profile / Website Requirements / target Proposal versions and identities.
- Page, route, navigation, section and visible element structure in the target Proposal.
- Canonical functional requirements the Proposal is authorized/expected to realize.
- Unknowns/conflicts that must remain unresolved.
- Runtime Profile capabilities and prohibitions.
- Authorized Integration Contracts and missing integration authority.
- Development Base/scaffold, package manifest, lockfile, router, test setup, style system, assets and existing source organization.
- Existing tests/configuration that must not be weakened.

## Produce internally

Maintain a concise implementation plan: major source areas, expected page/section mapping, reusable components, functional bindings, likely tests, dependency needs and risks. Do not write this plan into the customer repository as an AI artifact.

## Blocker judgment

Block early only when meaningful completion is genuinely prevented by nonlocal authority/capability/upstream conditions. Missing preferred tooling or a difficult coding task is not a blocker if an authorized local solution exists.

## Boundary

Analysis does not redesign, reinterpret requirements, resolve conflicts, choose a provider, switch runtime, or add product scope.
